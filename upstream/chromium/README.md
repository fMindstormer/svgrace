# Chromium: syncbase begin lists resolve in exponential time

A report for the Chromium issue tracker, component **Blink>SVG**. The times are regenerated by
[`tools/cliff.py`](../../tools/cliff.py), which also writes the files the report attaches into this folder.

Only the fast files are kept in the repository: `grid-5.svg`, a control, and `maze-16x11-clocked.svg`.
`grid-6.svg`, `grid-7.svg` and `maze-16x11-syncbase.svg` freeze a Chromium tab for seconds to minutes,
and GitHub shows a clicked SVG file as an image, which would freeze the tab of anyone browsing here, so
`tools/cliff.py` writes them on your machine instead. Opening them in a Chromium-based browser freezes that
tab until the browser finishes; closing the tab ends it.

**Status:** not filed yet. Attach all five files.

---

**Title:** SMIL syncbase begin lists resolve in exponential time in the number of alternative routes

**Steps to reproduce**

1. Open the attached `grid-6.svg` (5 KB, no script): a 6×6 grid of 36 `<animate>` elements. Each begins
   0.1 s after the earliest of its neighbours, `begin="c1_0.begin+0.1s; c0_1.begin+0.1s"`, with
   `restart="never"`; `c0_0` begins at `0s`.
2. Open `grid-7.svg`, the same with 49 elements.
3. Optionally, show `grid-6.svg` through a plain `<img>` in any page.

**Expected:** the files load at once, and the far corner begins at (2k − 2) × 0.1 s: 1.0 s for 6×6. Firefox
and WebKit load all of them in well under a second, with the correct start times.

**Actual:** the renderer's main thread is busy at load for 12–15 s with `grid-6.svg`, and for over 100 s
with `grid-7.svg` (the measurement stopped there). Nothing on the page responds meanwhile. Shown through a
plain `<img>` in another page, `grid-6.svg` delays that page's load event by about 17 s. Each added row or column
multiplies the time, which points at the order in which begin times are resolved rather than at the
amount of work:

| File | Timing | Chromium 156 | Firefox 157 | WebKit 27.2 |
|---|---|---|---|---|
| perfect maze 24×16 (384 cells) | syncbase | 0.04 s | 0.09 s | 0.05 s |
| perfect maze 32×20 (640 cells) | syncbase | 0.05 s | 0.11 s | 0.06 s |
| braid maze 12×9 (108 cells) | syncbase | 0.06 s | 0.11 s | 0.02 s |
| braid maze 14×10 (140 cells) | syncbase | 2.49 s | 0.11 s | 0.02 s |
| braid maze 16×11 (176 cells), `maze-16x11-syncbase.svg` | syncbase | 50.19 s | 0.12 s | 0.02 s |
| the same maze, `maze-16x11-clocked.svg` | event-based | 0.03 s | 0.12 s | 0.03 s |
| braid maze 40×30 (1,200 cells) | event-based | 0.10 s | 0.23 s | 0.12 s |
| `grid-5.svg` (25 animations) | syncbase | 0.08 s | 0.10 s | 0.01 s |
| `grid-6.svg` (36 animations) | syncbase | 15.09 s | 0.10 s | 0.02 s |
| `grid-7.svg` (49 animations) | syncbase | over 100 s (stopped) | 0.10 s | 0.01 s |

Time from handing the document to the page until it has loaded and answers a script, in Playwright's
builds (Chromium 156.0.8078.4, Firefox 157.0, WebKit 27.2) on an Apple-silicon Mac. Repeated runs vary:
12–15 s for `grid-6.svg`, 50–80 s for the 176-cell maze.

The start times Chromium computes are correct, only slow. Perfect mazes (one route between any two cells)
load at once at any size, and so do the same mazes built with event-based timing.

**Analysis**

A begin list takes its earliest instance time, so each `begin="A.begin+d; B.begin+d"` is one relaxation
step of a shortest-path problem, and the engine solves the whole graph at load. In
`third_party/blink/renderer/core/svg/animation/svg_smil_element.cc`, every change propagates at once and
depth-first: `SetNewInterval` → `NotifyDependentsOnNewInterval` → `NotifyDependents` →
`CreateInstanceTimesFromSyncBase` → `InstanceListChanged` → `UpdateInterval` → `SetNewInterval` on each
dependent, before the next dependent is visited.

That is a label-correcting shortest-path search in depth-first order, whose worst case is exponential.
With alternative routes (open cycles in the time graph), an element is often reached first along a long
detour; the time it then propagates is improved later along a shorter route, and the improvement is
propagated again through everything downstream, including the later cycles, which each repeat the
pattern. Without alternative routes nothing is ever improved, which is why trees stay fast. The `FIXME` in
`CreateInstanceTimesFromSyncBase` ("this should handle updating existing interval by changing the
associated times instead of creating new ones") adds to it: each notification appends instance times, so
the lists grow with every correction.

SMIL 3.0 describes this stack-like propagation in its informative section on detecting cycles
(https://www.w3.org/TR/SMIL3/smil-timing.html, "Detecting Cycles"), so the implementation follows the
specification's suggestion; Firefox and WebKit show the same documents can be resolved quickly.

**Possible fixes:** queue elements whose instance lists changed and process them in order of the changed
time, the way Dijkstra's algorithm does, which settles each element once when offsets are non-negative;
or process the queue first-in first-out, which is polynomial with any offsets. Updating the instance times
that came from one syncbase instead of appending new ones would keep the lists bounded.

**Workaround:** event-based conditions (`c0_0.beginEvent+0.1s`) are resolved as the clock runs, in time
order, and load at once (table above).

**Related:** the 2019 rework of dependents notification (crbug.com/998526) and the CHECKs added for
infinite loops and hangs in `ResolveInterval` (crbug.com/1021630).

**Found by:** svgrace, https://github.com/fMindstormer/svgrace, which compiles mazes into SVGs whose
animation timing finds the cheapest route.

**Version:** Chromium 156.0.8078.4 (Playwright 1.64 headless shell) on macOS, arm64; first seen in
Chromium 141 on Linux, where a 216-cell braid maze took over 5 minutes.
